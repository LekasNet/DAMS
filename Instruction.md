# DAMS — VS Code Extension & Baker

## Цель проекта

Разработать полноценное расширение для Visual Studio Code, поддерживающее формат **DAMS (Data Associated Markup Standart) v0.3**.

Расширение должно обеспечивать:

1. Подсветку синтаксиса DAMS.
2. Синтаксическую и семантическую диагностику.
3. Quick Fix для строковых ключей и преобразований `object`/`dict`.
4. Автодополнение объектных путей.
5. Переход к объявлениям и переименование полей.
6. Baking — вычисление документа с заменой всех ссылок и выражений конечными значениями.
7. Предпросмотр запечённого документа.
8. Сохранение результата Baking в отдельный файл.

**Главное требование:** реализация должна соответствовать приложенному документу `DAMS_v0.3_specification.md`.

Если правила спецификации неоднозначны, не следует молча придумывать новое поведение. Изолировать такое решение, документировать его и покрывать тестами.

## 1. Технологии

Использовать:

- TypeScript с включённым `strict`.
- Node.js.
- VS Code Extension API.
- TextMate Grammar для базовой подсветки.
- Собственный tokenizer, parser и evaluator.
- AST для представления документа.
- Vitest для модульных тестов.
- esbuild для сборки расширения.

Не использовать `eval()`, `new Function()` или JavaScript-движок для выполнения выражений DAMS.

Не использовать `JSON.parse()` как основной парсер DAMS.

Парсер должен быть собственной реализацией грамматики DAMS.

## 3. Lexer и Parser

Реализовать полноценный разбор DAMS на основе спецификации v0.3.

Поддержать:

- Объявления через `:`.
- Аннотации `(type)`.
- `object`, `dict`, `array`.
- Все предусмотренные примитивные значения.
- Строковые ключи.
- Комментарии `//`.
- Разделители в виде запятых и переносов строк.
- Продолжение выражений после операторов.
- Арифметические операторы.
- Оператор конкатенации `&`.
- Объектные обращения.
- Относительные обращения `.Field`.
- Индексацию и срезы.
- Вложенные выражения и круглые скобки.

Парсер должен строить AST, сохраняя `SourceRange` каждого узла.

AST должен сохранять исходные выражения, а не немедленно заменять их результатами.

При ошибке парсер должен по возможности продолжать разбор документа, чтобы отображать несколько диагностик одновременно.

## 4. Система значений

Реализовать типы DAMS v0.3.

Особое внимание уделить:

- Сохранению ведущих нулей HEX/BIN/OCT.
- Приведению представлений при конкатенации.
- Выравниванию по байтам.
- Детерминированной десятичной арифметике.
- `undefined` как самостоятельному конечному значению.
- Различию между `object` и `dict`.

Не использовать JavaScript `number` для арифметики, требующей произвольной точности.

Использовать `bigint` для целых значений и подходящую библиотеку десятичной арифметики для `float`.

Числовая семантика должна соответствовать спецификации.

## 5. Resolver и Evaluator

Реализовать разрешение путей и ленивое вычисление зависимостей.

Пример:

```dams
Data: {
    A: 10
    B: .A * 2
    C: .B + 5
}
```

Запрос `Data.C` должен возвращать `25`.

Порядок:

1. Найти узел `Data.C`.
2. Обнаружить зависимость от `Data.B`.
3. Разрешить зависимость `Data.B` от `Data.A`.
4. Получить значение `Data.A`.
5. Вычислить `Data.B`.
6. Вычислить `Data.C`.

Реализовать детектирование циклических зависимостей.

Обращение к несуществующим полям должно возвращать `undefined`, а не выбрасывать исключение.

`undefined` должен распространяться по зависимым выражениям согласно спецификации.

При изменении исходного документа все зависимые значения должны актуализироваться. Для первоначальной реализации допустимо повторное вычисление при чтении, без сложной системы реактивности.

## 6. Baker

Baker — одна из главных функций расширения.

Он должен преобразовывать исходный DAMS-документ в полностью вычисленный DAMS-документ.

Пример входа:

```dams
Services: {
    ReadDID: 0x22
}

DIDs: {
    VIN: 0xF190
}

Requests: {
    ReadVIN: Services.ReadDID & DIDs.VIN
    Timeout: 100 * 3
    DID: DIDs.VIN
}
```

Ожидаемый выход:

```dams
Services: {
    ReadDID: 0x22
}

DIDs: {
    VIN: 0xF190
}

Requests: {
    ReadVIN: 0x22F190
    Timeout: 300
    DID: 0xF190
}
```

Правила Baking:

- Все обращения разрешаются.
- Все выражения вычисляются.
- Все композиции материализуются.
- Все аннотации удаляются.
- `undefined` сохраняется.
- Строковые ключи сохраняются без преобразования.
- Порядок полей не изменяется.
- Ведущие нули и представления бинарных данных сохраняются по правилам спецификации.
- Результат не содержит ссылок и вычисляемых выражений.
- Исходный файл никогда не изменяется автоматически.

Baker должен возвращать структурированный результат с диагностикой.

При фатальных ошибках вычисления нельзя создавать частично запечённый файл и выдавать его за успешный результат.

## 7. Syntax Highlighting

Реализовать TextMate Grammar для `.dams`.

Подсвечивать раздельно:

- Имена объявлений.
- Строковые ключи.
- Аннотации.
- Строковые значения.
- Целые и дробные числа.
- HEX/BIN/OCT.
- Boolean.
- `null` и `undefined`.
- Объектные пути.
- Арифметические операторы.
- Конкатенацию `&`.
- Скобки и разделители.
- Комментарии.

Подсветка должна использовать стандартные semantic scopes VS Code и корректно работать со светлыми и тёмными темами.

Не задавать жёсткие цвета для каждой конструкции.

## 8. Диагностика

Реализовать `DiagnosticCollection`.

Отображать ошибки:

- Некорректного синтаксиса.
- Повторяющихся ключей.
- Нарушений ограничений `dict`.
- Неподдерживаемых аннотаций.
- Несовместимых типов.
- Циклических зависимостей.
- Ошибок арифметики.
- Отрицательных индексов и срезов.
- Некорректной конкатенации.

Отсутствующее поле, возвращающее `undefined`, не должно автоматически считаться синтаксической ошибкой.

Предупреждения IDE и ошибки языка должны быть разделены.

Диагностику обновлять по мере изменения документа, с debounce и защитой от устаревших результатов.

## 9. Quick Fix для строковых ключей

Для обычного `object` реализовать рекомендацию по преобразованию строкового ключа в идентификатор.

Если строковый ключ уже является допустимым идентификатором, отображать предупреждение:

`String key can be an object name`

Предоставлять Quick Fix.

Для ключей с пробелами реализовать предложенный алгоритм:

1. Разделить ключ на слова.
2. Для каждой границы сравнить последний символ предыдущего слова и первый символ следующего слова.
3. Если регистр одинаковый — заменить пробел на `_`.
4. Если регистр отличается — удалить пробел.
5. Проверить корректность результирующего идентификатора.
6. Проверить отсутствие конфликта с существующими ключами.
7. При возможности безопасно обновить все ссылки.

Обязательные тесты:

```text
"Full Name"     -> FullName
"First name"    -> First_name
"XML Database"  -> XML_Database
"Read DID"      -> ReadDID
"Vehicle speed" -> Vehicle_speed
```

И полный пример:

```text
"Drop XML Database direction Forever Young"
```

Должен преобразовываться в:

```text
DropXML_Database_directionForeverYoung
```

Для `dict` предупреждения и соответствующий Quick Fix не показывать.

В сомнительных случаях не выполнять небезопасный автоматический рефакторинг.

## 10. IntelliSense и навигация

После реализации стабильного AST добавить:

- Completion Provider для путей.
- Definition Provider для перехода к объявлению.
- Hover Provider для отображения текущего значения.
- Rename Provider для безопасного переименования.
- Document Symbol Provider для структуры файла.

Пример:

```dams
Data: {
    Field_1: 10
    Field_2: 20
}

Other: {
    Value: Data.
}
```

После `Data.` показывать `Field_1` и `Field_2`.

Hover по выражению должен показывать вычисленное значение либо краткую диагностическую информацию.

Не вычислять всё содержимое файла заново для каждого пользовательского действия, если доступен актуальный результат анализа.

## 11. Команды VS Code

Зарегистрировать команды:

- `DAMS: Bake Current File`
- `DAMS: Preview Baked Result`
- `DAMS: Validate Current File`

Команды Baking должны использовать только core Baker, не реализуя вычисления повторно в Extension.

**Bake Current File:** сохранить результат рядом с исходным файлом с именем `<name>.baked.dams`.

**Preview Baked Result:** открыть виртуальный документ VS Code, не создавая файл на диске.

**Validate Current File:** выполнить полный синтаксический и семантический анализ и показать диагностические сообщения.

Ошибки должны попадать в панель Problems, а при запуске команд — отображаться в понятном виде.

## 13. Порядок разработки

Работать последовательно.

**Этап 1 — Core**

Lexer, Parser, AST, типы значений, Resolver, Evaluator и Baker.

**Этап 2 — Тесты ядра**

Проверка вычислений, ссылок, арифметики, конкатенации и сериализации.

**Этап 3 — Базовое расширение**

Регистрация `.dams`, TextMate Grammar, конфигурация языка, команды Baking.

**Этап 4 — Диагностика**

Ошибки, предупреждения, подсветка проблемного диапазона.

**Этап 5 — Работа с кодом**

Quick Fix, Completion, Hover, Definition, Rename.

**Этап 6 — Завершение**

Интеграционные тесты, документация, упаковка VSIX.

Не переходить к сложным возможностям редактора раньше, чем готово и протестировано ядро.

## 14. Критерии готовности

Проект считается завершённым, когда:

- Расширение запускается в VS Code Extension Development Host.
- Файлы `.dams` распознаются автоматически.
- Подсветка работает на всех основных конструкциях.
- Диагностика выводит корректные сообщения и диапазоны.
- Quick Fix работает по согласованным правилам.
- Baker вычисляет все выражения и ссылки.
- Результат Baking повторно разбирается DAMS-парсером.
- Отсутствуют известные расхождения с нормативными правилами v0.3.
- Тесты проходят.
- Проект собирается в `.vsix`.

## 15. Требования к качеству

Не писать всю логику в одном файле.

Не связывать вычисления с UI редактора.

Не заменять полноценный Parser регулярными выражениями.

Не изменять оригинальные DAMS-документы во время Baking.

Не делать вид, что неподдерживаемая конструкция обработана успешно.

Сохранять тестируемость каждого слоя.
