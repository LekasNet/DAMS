# DAMS — Data Associated Markup Standart

**Спецификация:** v0.3  
**Статус:** draft / проект стандарта  
**Язык документа:** русский  
**Совместимость:** развивает DAMS v0.2; не является реализацией парсера.

> **Разделение статусов правил.** Пометка **Норма** означает согласованное поведение формата. **Профиль v0.3** — выбранный для взаимно совместимых реализаций технический вариант там, где пользователь делегировал выбор (прежде всего деление). **Открыто** — решение ещё не согласовано. Ненормативные примеры и IDE-рекомендации не меняют семантику.

## 1. Назначение и модель

DAMS — текстовый формат связанных структурированных данных. Он сочетает JSON-подобные объекты и массивы, выражения, доступ по путям и конкатенацию `&`. Исходный документ описывает **граф зависимостей**; операция **Baking** полностью вычисляет документ в независимое дерево конечных значений в синтаксисе DAMS. Baking не является частичным и не изменяет исходник.

Файл обычно содержит несколько полей на верхнем уровне, без обязательной внешней пары `{}`:

```dams
Services: { ReadDID: 0x22 }
DIDs: { VIN: 0xF190 }
Requests: { ReadVIN: Services.ReadDID & DIDs.VIN }
```

**Норма:** явные объявления через "=" отсутствуют: все поля объявляются через `:`. Повтор ключа в одном объекте — ошибка. Порядок ключей сохраняется.

## 2. Ключи и объявления

```dams
Field: 10
Field2 (float): 10
"String key": "value"
Values (dict): { "A": 1, "B": 2 }
```

- Идентификатор: `[A-Za-z_][A-Za-z0-9_]*`. Дефис запрещён; регистр значим.
- Строковый ключ — строковый литерал в двойных кавычках: разрешены пробелы, точки, символы `$` и т. п.
- Имена `Key` и `"Key"` обозначают одинаковый ключ внутри **object** и потому конфликтуют при совместном объявлении.
- Аннотация пишется **после ключа, перед двоеточием**: `Name (annotation): expression`.
- Парсер не меняет написание ключей автоматически.
- В `dict` допустимы **только ключи, записанные строковыми литералами**, даже если их текст допустим как идентификатор. IDE не выдаёт предупреждений о кавычках внутри `dict`.

### 2.1. `object` и `dict`

`dict` — более строгая разновидность `object`, а не отдельная группа для `&`:

```dams
Obj: { Name: "Ann" }
Map (dict): { "City": "Oslo" }
Combined: Obj & Map          // object
Invalid (dict): Obj & Map    // ошибка: недопустимое сужение object → dict
Empty: {}                    // object
EmptyMap (dict): {}          // dict
```

**Норма:** `dict → object` допустимо; обратное преобразование данных автоматически не выполняется. Редактор может предложить Quick Fix по переводу ключей в строковую запись. `object & object`, `object & dict`, `dict & object`, `dict & dict` допускаются при отсутствии конфликтующих ключей верхнего уровня; тип без аннотации выбирается по более общему типу (если оба `dict`, результат `dict`). Аннотация `(dict)` для композиции с операндом типа `object` даёт ошибку. Переход `object → dict` не выполняется даже если все ключи объекта случайно строковые.

## 3. Строки и комментарии

- Поддерживаются **только** две интерпретируемые escape-последовательности: `\"` → кавычка и `\\` → один обратный слеш.
- Любая иная комбинация `\` с последующим символом сохраняется **буквально**, без ошибки: `\n` — символы `\` и `n`, не перевод строки.
- Это относится к значениям и строковым ключам.
- Строки заключаются в `"..."`; обычный реальный перенос строки внутри строки не допускается; отдельный синтаксис многострочных строк не вводится.
- `//` вне строки начинает однострочный комментарий.

```dams
A: "Hello \"World\""
B: "String like \\"
C: "C:\Users\Documents"  // обратные слеши перед U и D — буквальные
D: "literal \n text"     // не содержит перевода строки
```

**Замечание по сериализации:** символы `"` и `\` при выводе должны быть экранированы, чтобы повторный разбор восстановил то же строковое значение.

## 4. Разделители, скобки, переносы

- Между соседними полями и элементами массива используется **запятая или перевод строки**.
- Если два элемента находятся на одной строке, запятая обязательна: `{A: 1, B: 2}` корректно, `{A: 1 B: 2}` — ошибка.
- Запятая после последнего элемента разрешена.
- Если строка выражения оканчивается бинарным оператором, выражение продолжается на следующей строке.
- Если объявление заканчивается `:`, значение допускается на следующей **непустой** строке.
- `(...)` — группировка выражений; аннотация определяется только в позиции после ключа.

```dams
Request:
    Services.ReadDID &
    DIDs.VIN
Items: [1, 2, 3,]
```

**Открыто:** финальные лексические детали многострочной группировки `(...)` и пропуска комментариев между строками следует проверить тестами грамматики. Во всех примерах документа однозначное продолжение заканчивается оператором.

## 5. Значения и представления

| Категория | Аннотация | Литерал / пример | Свойства |
|---|---|---|---|
| Число целое | `int` | `42`, `-10` | Без фиксированной битности |
| Число десятичное | `float` | `3.14`, `-0.5` | Произвольный масштаб; профиль вычислений — §9 |
| Представление по основанию 16 | `hex` | `0x0022` | Неотрицательное; ведущие нули значимы |
| Представление по основанию 2 | `bin` | `0b00001010` | Неотрицательное; ведущие нули значимы |
| Представление по основанию 8 | `oct` | `0o017` | Неотрицательное; ведущие нули значимы |
| Строка | `string` (алиас `str`) | `"text"` | Экранирование §3 |
| Логическое | `bool` | `true`, `false` | Без логических операторов |
| Пустое значение | `null` | `null` | Конечный литерал |
| Неопределённое | `undefined` | `undefined` | Конечный литерал любого ожидаемого типа |
| Массив | `array` | `[1, 2]` | Порядок элементов значим |
| Объект | `object` | `{A: 1}` | Идентификаторы и строковые ключи |
| Словарь | `dict` | `(dict): {"A": 1}` | Подтип `object`, только строковая запись ключей |

**Норма:** `int` и `float` — представления числовых значений, а не фиксированные machine-типы. HEX/BIN/OCT — представления неотрицательных числовых/битовых данных, но их **длина записи сохраняется**. Отрицательных HEX/BIN/OCT нет. Для числа с дробной частью `(int)` недопустим; `(float)` от целого допустим.

### 5.1. Аннотации и преобразования

```dams
A (hex): 255          // 0xFF
B (float): 10         // численно 10; допускается отображение без .0
C (string): 123       // "123"
Bad (int): 3.5        // ошибка
```

- Аннотация задаёт **желаемое представление результата**, а не обязательность вручную типизировать каждое поле.
- Неявное расширение целого в `float` допустимо; сужение дробного до `int` — ошибка.
- Для `(string)` числовое значение преобразуется в его текстовое представление.
- `undefined` допустим при любой аннотации и остаётся `undefined` после Baking.
- HEX/BIN/OCT приводятся к заданному основанию, при необходимости сохраняется и дополняется разрядность до **целого байта** (§8).

**Открыто:** полный перечень допустимых явных преобразований `null`, `bool`, массивов и текстовых строк к числам не утверждён. Реализация не должна молча придумывать их.

## 6. Путь, ссылки и область видимости

```dams
Block: {
    SubBlock: {
        A: 10
        B: .A * 2
        C: .B + 5
    }
}
Result: Block.SubBlock.C
```

- `Block.SubBlock.C` — абсолютный путь от корня.
- `.A` — соседнее поле того же объекта, где объявлен текущий узел; это не переход к родителю.
- `Object["String key"]` — доступ к любому ключу по строке; для обычного имени `.Name` и `["Name"]` эквивалентны на `object`.
- Для `dict` используется `Map["Name"]`, но **не** `Map.Name`.
- Отсутствующий сегмент пути возвращает `undefined`; доступ через уже полученный `undefined` также возвращает `undefined`.
- Ссылки — **живые ссылки на путь**. Они разрешаются повторно при чтении; цепочка ссылок допустима.
- Любые циклические зависимости, в том числе косвенные, — ошибка; самоссылка — ошибка.
- Записи или переназначения исходного узла через ссылочное выражение синтаксис DAMS не предоставляет; изменение исходного документа/модели выполняет программа.

### 6.1. Вычисление зависимостей при чтении

```dams
Data: {
    A: 10
    B: .A * 2
    C: .B + 5
}
```

Чтение `Data.C` разрешает `.B`, затем `.A`, затем вычисляет `10 * 2 = 20`, `20 + 5 = 25`. Если runtime изменяет `A` на `20`, последующее чтение `C` даёт `45`. Библиотека свободна вычислять заново, вести кэш с корректной инвалидацией или уведомлять наблюдателей. **Нормируется наблюдаемый результат, но не механизм реактивности.**

## 7. Индексация и срезы

Индексация с нуля. Срез `[start:end]` включает `start`, исключает `end`. Отрицательные индексы и границы — **ошибка**. Неотрицательный индекс вне диапазона — `undefined`. Срез за правую границу **дополняет конечный результат `undefined`** до требуемой длины:

```dams
A: [10, 20]
B: A[1:4]          // [20, undefined, undefined]
```

- Для `array` единица доступа — элемент верхнего уровня.
- Для `hex`, `bin` и `oct` единица доступа — **байт, а не цифра и не бит**; все три основания трактуются как одно и то же последовательное байтовое представление.
- Для неполного последнего/первого байта запись при операциях с байтами **дополняется ведущими нулями до целого байта**; порядок байтов — слева направо от наиболее значимого байта.

```dams
Payload: 0x22F190
First: Payload[0]     // 0x22
Second: Payload[1]    // 0xF1
Tail: Payload[1:3]    // 0xF190
Short: 0xF
Padded: Short[0]     // 0x0F
```

**Открыто:** посимвольная индексация строк (Unicode code points или grapheme clusters) пока не нормируется; строковые срезы не следует считать обязательной функцией v0.3.

## 8. Оператор композиции `&`

Компонуются **только значения одной группы**: (1) данные/скаляры, (2) массивы, (3) объекты, включая `dict`. Межгрупповая композиция — ошибка. Это **не** побитовое AND и **не** арифметика, а конкатенация.

### 8.1. Скаляры

В группе данных операнды сначала преобразуются к **представлению результата**, затем текстовые последовательности без префиксов объединяются. Представление результата задаёт аннотация; без неё — **тип/представление первого операнда**.

```dams
A: 0x22 & "F190"           // 0x22F190
B (str): 0x22 & "F190"     // "22F190"
C: 10 & 0x22               // 1034
D (hex): 10 & 0x22         // 0x0A22
```

**Норма:** при целевом HEX/BIN/OCT разрешённые числовые операнды приводятся к выбранному основанию, сохраняются значимые ведущие нули, неполные байты дополняются **слева** до целого байта. При целевом `str` префиксы `0x/0b/0o` убираются. При целевом `int` для примера `10 & 0x22` второй операнд сначала переводится в десятичное `34`, потом образуется десятичная запись `1034`. Для строк при числовой композиции содержимое используется как **последовательность цифр целевого основания**: `"F190"` допустимо в hex-контексте, а строка с недопустимыми цифрами — ошибка.

**Профиль v0.3:** для операций с BIN/HEX/OCT считается значимой битовая длина записанных разрядов. При конвертации в другое основание ширина сначала округляется **вверх до кратной 8 битам**, затем выводится необходимое количество цифр выбранного основания (для `oct` — `ceil(bits/3)`); если требуется, дополняется нулями слева. `0xF` тем самым соответствует байту `0x0F`. Обычный неотрицательный `int`, используемый как байтовый компонент, занимает минимальное число целых байтов (0 занимает 1 байт). Результат `0x0A22` для `(hex): 10 & 0x22` следует именно этому правилу.

**Открыто:** универсальная композиция произвольных дробных `float` с данными не определена; примеры с дробными значениями следует считать ошибкой до утверждения правил сериализации.

### 8.2. Массивы

Объединяются **только элементы верхнего уровня**, слева направо:

```dams
A: [1, [2, 3]]
B: [4, 5]
C: A & B             // [1, [2, 3], 4, 5]
```

### 8.3. Объекты

Создаётся новый объект со всеми полями верхнего уровня в порядке операндов. Дублирующиеся ключи на объединяемом уровне — ошибка, независимо от записи ключа в кавычках. Совпадающие имена в **разных вложенных** объектах не конфликтуют. Правила `object/dict` — §2.1.

## 9. Арифметика и детерминированная точность

Операторы: `+`, `-`, `*`, `/`, унарные `+` и `-` для допустимых числовых типов. Стандартная арифметика: `*` и `/` выше `+` и `-`. Приоритет от высокого к низкому: пути/индексы; скобочная группировка; `&`; `*`, `/`; `+`, `-`. Скобки меняют порядок. Логических и побитовых операций нет.

- Арифметика допускается между `int`, `float`, `hex`, `bin`, `oct` при числовой совместимости.
- Если хотя бы один операнд `float`, результат арифметики имеет числовую семантику `float`. Явная аннотация, противоречащая дробному результату, — ошибка.
- Отрицательное значение нельзя материализовать как `hex`, `bin` или `oct`.
- Любая арифметическая формула с `undefined` даёт `undefined`, если ранее не возникла самостоятельная ошибка (например, недопустимый оператор для типа).
- Деление на ноль — ошибка.

### 9.1. Профиль численной точности v0.3

Пользователь потребовал **неограниченную фиксированной машинной разрядностью численную модель**, но деление вроде `1/3` не имеет конечной десятичной записи. Для одинакового Baking во всех языках принят следующий **профиль по умолчанию**:

1. Целые (`int`) хранятся с произвольной длиной, **точно**, без переполнения.
2. Конечные десятичные литералы и результаты операций без деления представляются как точные десятичные числа с произвольным количеством знаков (например, `0.1 + 0.2` точно `0.3`).
3. Деление сначала вычисляется как отношение точных значений. Если десятичная запись **конечная**, результат сохраняется точно независимо от длины (например, `1 / 8 = 0.125`).
4. Если десятичная запись **бесконечная**, результат округляется до **34 значащих десятичных цифр** по правилу **round half to even** (банковское округление); округление производится **в точке деления**, а не задним числом при Baking. Последующие операции используют уже округлённое значение.
5. Экспонента/масштаб не имеют машинных ограничений в модели. Реализация может иметь задокументированные ограничения ресурсов и должна **явно выдавать ошибку лимита**, а не незаметно менять численное значение.
6. Округление с 34 значащими цифрами — стандартный профиль DAMS v0.3; в будущем возможны версионированные профили, но результат Baking v0.3 не должен зависеть от локальных настроек Decimal/context процесса.

Примеры:

```dams
A: 0.1 + 0.2          // 0.3
B: 1 / 8              // 0.125
C: 1 / 3              // 0.3333333333333333333333333333333333 (34 значащие цифры)
D: 10 / 2             // математически 5; допускается вывод 5 без .0
```

**Ограничение на сохранение типа:** пользователь разрешил вывод целочисленно выглядящих значений `float` без `.0`, поэтому повторный парсинг Baked может интерпретировать `5` как `int`. В v0.3 нормативно сохраняется **числовое значение**, а гарантированная идентичность подтипа `float` после повторного чтения Baked **не обещается**. Это осознанное следствие удаления аннотаций, не скрытое преобразование.

**Открыто:** точное правило выбора числового представления после смешанной целочисленной арифметики HEX/BIN/OCT без аннотации — предлагается оставить представление первого операнда, но решение ещё не подтверждено. В тестах реализации этот случай отмечается как требующий спецификации.

## 10. `undefined`, ошибки, зависимости

`undefined` — самостоятельное конечное значение, допускается с любой аннотацией. Неизвестный путь → `undefined`, дальнейшие сегменты у `undefined` → `undefined`, арифметическое выражение с таким операндом → `undefined`.

**Ошибки:** недопустимый синтаксис, повтор ключа, цикл в графе зависимостей, незаконное преобразование типа, межгрупповое `&`, повтор ключа при слиянии объектов, отрицательный индекс или граница, деление на ноль, недопустимая операция и нарушение согласованных правил аннотаций.

**Не ошибки:** отсутствующий путь, положительный индекс вне диапазона, выход среза за правую границу, trailing comma, неизвестная после `\` последовательность внутри строки (она просто буквальная).

## 11. Baking

**Baking — одна полная, однозначная операция.** Baker вычисляет все выражения, ссылки и композиции; материализует их в независимые конечные литералы и коллекции; удаляет аннотации; оставляет `undefined` как литерал. Оригинальный документ не меняется. Порядок полей и оригинальные строковые ключи сохраняются. Для бинарных значений сохраняются основание и длина (с применением правил дополнения только там, где преобразование их требует).

```dams
// Source
Config: { Base: 100, Multiplier: 3, Total: .Base * .Multiplier }
Services: { Read: 0x22 }
DIDs: { VIN: 0xF190 }
Requests: { VIN: Services.Read & DIDs.VIN, BadPath: Missing.Name }
```

```dams
// Baked
Config: { Base: 100, Multiplier: 3, Total: 300 }
Services: { Read: 0x22 }
DIDs: { VIN: 0xF190 }
Requests: { VIN: 0x22F190, BadPath: undefined }
```

**Норма:** после Baking живые связи отсутствуют; изменение одного значения Baked не изменяет другие. Если в документе цикл или ошибка вычисления, Baking не выдаёт успешный результат.

## 12. Грамматика: рабочий EBNF-скелет

Ниже **не окончательная проверенная формальная грамматика**, а рабочий каркас для парсера. `SEP` обозначает запятую или значимый перевод строки; точная лексическая обработка `SEP`, продолжений и аннотаций — отдельная стадия.

```ebnf
Document     = { Separator | Member } ;
Member       = Key, [ Annotation ], ":", Expression ;
Key          = Identifier | String ;
Annotation   = "(", Identifier, ")" ;
Expression   = Additive ;
Additive     = Multiplicative, { ("+" | "-"), Multiplicative } ;
Multiplicative = Concatenation, { ("*" | "/"), Concatenation } ;
Concatenation = Unary, { "&", Unary } ;
Unary        = [ "+" | "-" ], Primary ;
Primary      = Atom, { PathPart } | "(", Expression, ")" ;
PathPart     = ".", Identifier | "[", (String | Integer | Slice), "]" ;
Slice        = Integer, ":", Integer ;
Atom         = Literal | Identifier | ".", Identifier | Object | Array ;
Object       = "{", { Separator | Member }, "}" ;
Array        = "[", { Separator | Expression }, "]" ;
Separator    = "," | NEWLINE ;
Identifier   = ("A"…"Z" | "a"…"z" | "_"), { "A"…"Z" | "a"…"z" | "_" | "0"…"9" } ;
Literal      = Number | String | "true" | "false" | "null" | "undefined" ;
```

Важные условия вне EBNF: абсолютный путь начинается с корневого имени, `.Field` — соседний; ссылки разбираются как выражения; двусмысленность `(...)` устраняется позицией после `Key`; отсутствие разделителя на одной строке — ошибка. Сканер строк распознаёт только `\"` и `\\`; остальные пары с `\` оставляет буквально.

## 13. IDE и Quick Fix (рекомендации, не синтаксис)

Строковые ключи в `object` разрешены, но редактор **может** жёлтым подчёркивать строковый ключ, если ему возможно безопасно предложить обычный идентификатор с диагностикой `String key can be object name`. В `dict` **нет такого предупреждения**.

Алгоритм нормализации ключа с пробелами сравнивает **последнюю букву предыдущего слова и первую букву следующего**:

- Если обе латинские буквы одного регистра (`lower/lower` или `upper/upper`), заменить пробел на `_`.
- Если регистры разные (`lower/upper` или `upper/lower`), убрать пробел.
- Регистр букв не изменять; применять правило слева направо ко всем границам.

| Строковый ключ | Quick Fix |
|---|---|
| `"Full Name"` | `FullName` |
| `"First name"` | `First_name` |
| `"XML Database"` | `XML_Database` |
| `"Read DID"` | `ReadDID` |
| `"Vehicle speed"` | `Vehicle_speed` |
| `"hello world"` | `hello_world` |
| `"Drop XML Database direction Forever Young"` | `DropXML_Database_directionForeverYoung` |

Если результат не является допустимым идентификатором, есть конфликт ключа, нестандартные границы (цифры, пунктуация) либо невозможно безопасно обновить ссылки, IDE **не выполняет** автоматическое небезопасное переименование. Рефакторинг добровольный, не часть Baking.

## 14. Универсальность: XML/JSON (ненормативно)

Объекты, массивы, строковые ключи и `dict` позволяют моделировать многие данные XML/JSON, в том числе исходные DDT-имена с пробелами и точками. **Это не обещание обратимого преобразования произвольного XML**: XML-атрибуты, пространства имён, повторяющиеся теги, смешанный текст/дочерние элементы, CDATA и инструкции обработки требуют соглашения конвертера; реальные семантические ссылки DDT необходимо извлекать со знанием предметной области.

## 15. Рекомендуемые этапы реализации (ненормативно)

1. Лексер (значимые переводы строк, комментарии, строковые escape), затем AST-парсер.
2. Модель значений, аннотаций и путей, диагностика дубликатов.
3. Разрешение живых ссылок и циклов, ленивый вычислитель выражений.
4. Отдельный слой `&`, числовые преобразования и точная арифметика.
5. Baker и канонический сериализатор, набор тестов для одинакового результата на Python/JS/Dart/Zig.
6. IDE-диагностика и Quick Fix как отдельный необязательный инструмент.

## 16. Открытые вопросы перед статусом normative

1. Полный набор разрешённых преобразований аннотаций, в частности `null`/`bool`, строка → число.
2. Что означает индексация и срезы **строк** и какой Unicode-уровень используется, если она будет включена.
3. Правило вывода основания **смешанной целочисленной арифметики** без аннотации.
4. Окончательная проверенная грамматика: переносы внутри скобок, унарные знаки, зарезервированные слова, литералы с экспонентой и `SEP`.
5. Каноническое текстовое представление `float` с учётом осознанной потери метки типа после Baking.
6. Составные `&` с дробным `float`: запрет в v0.3 либо отдельная нормированная форма записи.

**Итог:** в v0.3 согласованы основные правила и выбран вычислительный профиль деления с 34 значащими цифрами. Перечисленные открытые вопросы сохранены явно, а не замаскированы произвольными решениями автора документа.
